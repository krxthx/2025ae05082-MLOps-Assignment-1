This assignment builds an end-to-end MLOps pipeline for predicting the presence of heart disease from thirteen patient features. I use the UCI Heart Disease dataset, compare two classifiers, track experiments with MLflow, and serve the selected model through FastAPI. I will show the path from data and training to automated checks, Docker, Kubernetes, and monitoring.

The downloaded dataset contains three hundred and three rows, thirteen input features, and one binary target. There are one hundred and sixty-five positive cases and one hundred and thirty-eight negative cases, so the imbalance is mild. I checked missing values and duplicates and examined feature distributions and correlations. Evaluation uses shuffled, stratified folds to preserve class proportions and avoid bias from the dataset's ordering.

Preprocessing is part of the model pipeline. Numeric features receive median imputation and standard scaling. Categorical features receive most-frequent imputation and one-hot encoding, with unseen categories handled safely. Keeping preprocessing inside the pipeline fits it within each training fold and reuses it at inference. I tune Logistic Regression and Random Forest with five-fold stratified cross-validation. Random Forest is selected by the highest mean ROC-AUC: about zero point nine one eight, compared with zero point nine one seven for Logistic Regression. That margin is tiny, and Logistic Regression has higher recall. Tuning and evaluation reuse the same folds, so these estimates may be optimistic.

These are the tracked runs for the two candidate models. Each run records model parameters, tuned settings, accuracy, precision, recall, and ROC-AUC. The artifacts include grid-search results, an out-of-fold ROC curve, a confusion matrix, and the fitted model. This lets me inspect how a result was produced and compare experiments using the same evaluation setup.

The packaged joblib file contains both preprocessing and the selected classifier. Training and serving dependencies are pinned, with a smaller requirements file for the serving image. The seven tests cover the dataset contract, preprocessing, missing-value handling, model inference, and API validation. Here are the local test and lint results. GitHub Actions repeats linting, data acquisition, training, tests, and a Docker build. A failing step fails the workflow, and the artifact step preserves available metrics and screenshots.

The Docker image contains the saved pipeline and starts the FastAPI server. This health request confirms the API is reachable. I now submit the sample patient's thirteen features to the prediction endpoint. The saved model returns class one, labelled disease, with a positive-class probability of zero point six five two. The probability field always refers to the disease class. Input validation rejects invalid or incomplete requests before they reach the model. This is an educational model, rather than a tool for clinical decisions.

The same image is deployed to local Minikube using these manifests. The deployment requests two replicas and defines resource limits, readiness checks, and liveness checks. Here, both pods are ready, and the rollout has completed. The service is configured as a LoadBalancer. On this local setup, I access it through port-forwarding; a pending external IP does not prevent this demonstration. This request goes through the Kubernetes service and returns a prediction from the deployed model.

The monitoring stack runs the API, Prometheus, and Grafana. Prometheus scrapes the API every fifteen seconds; this target is up. After sending prediction requests, the Grafana dashboard displays prediction counts, request rates, latency, class distribution, and process CPU usage. The request logs connect an input with its prediction and probability. The disease-rate gauge can flag changes in predicted class mix, but it cannot establish model accuracy or confirm drift without further evidence and ground-truth labels.

The repository includes the download and training scripts, reusable pipeline, tests, CI workflow, deployment manifests, monitoring configuration, and report. This demonstration connects a reproducible experiment to a tested, containerised, locally deployed API with operational visibility. The main limitations are the small dataset, shared tuning and evaluation folds, and the absence of live ground-truth labels.
